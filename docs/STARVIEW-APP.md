# StarView and StarLock app source (Nov 11, 2026)

Kept in two places, the same text: this file in tsk-go/starview-data (`docs/STARVIEW-APP.md`) and
`claude/starview-app-source.md` in the StarView project on claude.ai. Update both together.

Both apps' source now lives in **tsk-go/starview-data** (public), Gradle project `app/`:
- `app/app` — StarView (tablet). Recovered from the 2.84.1 APK (Kotlin source was lost), checked method by method against its bytecode. Real decompiler bugs found and fixed on the way (endless loops in RoadShape/Hpms/VoiceDsp/curve editor, doubled corner points, takeovers logged twice, inverted camera-config flag).
- `app/starlock` — StarLock (phone). Recovered from 2.19 the same way; its library dex files rebuild byte-identical, only the app's code differs.
- `app/app/compile-stubs` — compile-only exception stubs (Kotlin has no checked exceptions); never packaged.
- `docs/tools/` — the comparison and scanning tools used for the recovery, and the off-device rendering test (see its README). `docs/pending/` — work written but not yet landed (only while there is some).

## Releases and updates
- Workflow `.github/workflows/starview-app.yml` builds both on every push to `main` that touches `app/`.
- A new `versionName` publishes a release: StarView `v<version>` (`StarView-<version>.apk`), StarLock `starlock-v<version>` (`StarLock-<version>.apk`, never marked "Latest").
- In-app updates: StarView Settings › Tablet › About › Check for updates; StarLock Updates › Check for updates (from 2.19.1).
- **Automatic updates (2.85.8, owner's choice Nov 11) — confirmed working end to end Nov 11:** every push to `main` with a new versionName reaches the tablet by itself ~1 min after the release — **also while driving**. Switch "Install updates automatically" (on by default, warning text) in Settings › Tablet › About. So: never push an unreviewed version to main; drafts stay on side branches. **Ask the owner before every release** (the session's safety check refused one push to main until he said go).
  - `AppUpdate.startAuto` (MainActivity.onCreate): daemon thread, GitHub `releases?per_page=10` once a minute with `If-None-Match` (a 304 is tiny and not counted against the limit); 403/429 -> 15 min pause; one try per version per 30 min; only an asset in state "uploaded"; never opens the "allow installs" screen by itself.
  - Install without the confirmation screen: `setRequireUserAction(USER_ACTION_NOT_REQUIRED)` + manifest `UPDATE_PACKAGES_WITHOUT_USER_ACTION` (Android 12+, self-update; tablet is Android 16, targetSdk 35 qualifies). Manual "Check for updates" installs are tap-free too.
  - Reopening after the install (Android closes the app and doesn't reopen it). Tested on the tablet: MY_PACKAGE_REPLACED's `startActivity` and the alarm-clock PendingIntent are both **blocked** by Android's background-activity rules (2.85.9 stayed closed). What works (2.85.10+): with "display over other apps" (SYSTEM_ALERT_WINDOW) allowed, `AppReplacedReceiver` (goAsync) adds a 1x1 TYPE_APPLICATION_OVERLAY window, starts MainActivity 0.5 s later, removes the window after 4 s (Android 15+ lets an SAW app start activities only while one of its windows is visible).
  - Where it comes back (2.85.12, owner's wish; confirmed with 2.85.13): `AppUpdate.inFront()` (own process importance == IMPORTANCE_FOREGROUND; 125 = only the LinkService) decides before the install. On screen -> marker "front", reopens on screen (+ the `Relaunch` alarms as extras). Another app in front or screen off -> marker "back", no toast, no alarm; MainActivity is started with extra `sv_back` + NO_ANIMATION and calls `moveTaskToBack(true)` in onCreate (and onNewIntent), so it runs again (comma link, turn signals, lane prompts, RTK corrections live in MainActivity; LinkService is only a keep-alive) behind the other app — at most a short flicker. The reopen behaviour of an update is the *installed* (old) version's: the first update after a change still behaves the old way.
  - The permission: `adb -d shell appops set com.starpilot.starview SYSTEM_ALERT_WINDOW allow` from the comma (HOME=/data/starview/adbhome) — only sticks once the installed version declares the permission (2.85.10+; on 2.85.9 it stayed "default"). Granted on the owner's tablet Nov 11. Settings › Tablet › About shows "Open again after an update" with an Allow button while it isn't granted (a reinstall / new tablet needs it again).
  - Comma-side backstop (openpilot patch 72, fork history 42): landed on tsk-go/openpilot Dom Nov 12 (`a691c92cc`). starviewd `Hub._reopen_check` from `tablet_flag_tick` — car on, tablet mode, tablet connected in the last 5 min, then no data client for 8 s -> `adb shell pidof com.starpilot.starview`; no process -> `_tablet_wake`. Every 20 s, 5 tries per drop; a running process is left alone, and it never pops up over another app (`_may_cover`: only over the home screen, the lock screen or nothing adb can tell; else it looks again 20 s later, within the 5 min). Test `starview/tests/test_reopen.py`. No longer needed for updates; still useful after a crash while driving.
- Drafts the owner hasn't approved go on a side branch (e.g. `navmap-fade`, `wheel-editor-map`, `map-free-size`), not `main`.

## How StarView is built: the hybrid (2.86.0, Nov 11)
Why: the recovered source is a decompiler's copy, and its mistakes (wrong casts, int instead of decimal, loops that never end) only show when that code runs — the Fix-button freeze on the lane card (2.85.13, `LaneFixDialog$Road.getER` looping) was one more. The owner wanted the root fixed, not patched again. So the shipped APK is no longer just our build: `app/hybrid/build.sh` (run by the workflow after Gradle) takes **2.84.1's own compiled code for everything we didn't change on purpose** and our build only for our own changes.
- Inputs: our Gradle APK, the original 2.84.1 APK (orphan branch `hybrid-base`, sha256-checked) and apktool 2.10.0 (its GitHub release, sha256-checked). Resources, manifest, native libs and assets are our build's; only the `classes*.dex` are replaced. Resource IDs stay 2.84.1's (`app/app/stable-ids.txt`, aapt2 `--stable-ids`) because the original code has them as numbers.
- Whole classes (`merge.py`): every class of 2.84.1 ships as it was, except `FEATURES` (our new or rewritten classes: HudLayout, NavOverlay/NavCardView/NavMapView/NavPos, AppUpdate…, Relaunch, Overlay, AnrWatch, R) and classes 2.84.1 doesn't have.
- Method by method (`methodmerge.py`, `decisions.py`, `patches.py`) for the classes we changed: MainActivity (with the screen tick `MainActivity$uiTick$1`), SettingsActivity, MapPane, HudEditor, WheelButton, UiSettings, LaneSuggest and VoiceNote (2.86.6), LaneBrain (2.87.0). Every method is 2.84.1's, except: `patch` = 2.84.1's code plus a few smali lines (written by `genpatch.py` from anchors) that call a small new method of ours named `hyb…` (in our source next to the code it stands for; our source calls it at the same place so both builds behave the same) or swap a constant / drop a block; `build` = our method (only `layoutMap`, `wireControls$lambda$136`, `floating_delegate$lambda$172` and UiSettings' defaults list, checked to equal 2.84.1's plus the `nav_map` item); new methods are always ours. Anything those need that 2.84.1 lacks (javac's anonymous classes, d8 accessors) comes along renamed `…$hyb…`; 2.84.1's private members they use lose `private` (or go through Kotlin's `access$` accessor).
- Checks, all in build.sh, any failure stops the release: `guard.py` — a changed source file must be in FEATURES or a method-level class, and every method that differs from the recovered source as first finished (`base.json`, from commit 755431e's build; `changes.py`) must have a decision; a method shipped as 2.84.1's code (`orig` / `patch`) carries the digest of our source at decision time, so editing it later fails the build until the patch is updated (`guard.py DIR --digests` prints the new ones). `check.py` — every call / field between the two halves resolves with the right access, static-ness, invoke kind, no final field written from outside. `verify.py` — register check of every changed method like Android's verifier (numbers vs objects vs long pairs vs unset, every path incl. catch blocks): no complaint on 3,035 of 2.84.1's own methods, and it catches a planted mistake (d8 re-dexing does not). CI builds with JDK 21 like base.json.
- **Changing StarView from now on:** edit the source as usual. If guard says a method "ships as 2.84.1's code", either port the change as a patch (add it in `genpatch.py`, run `genpatch.py ORIG_SMALI app/hybrid/patches.py`, record the digest) or make it `build` after checking that method by hand. New classes and new methods need nothing. Local run: `app/hybrid/build.sh app/app/build/outputs/apk/debug/app-debug.apk <2.84.1 apk> <apktool jar> out.apk`.
- Result in 2.86.0: of StarView's code, only our own new code and those three small methods come from our build; everything else, including the whole driving-screen tick, is the code 2.84.1 shipped.

## Finding freezes / crashes on the tablet
All from the comma, one block (`export HOME=/data/starview/adbhome` first):
- Why StarView last closed (crash / freeze / update / swiped away, newest first): `adb -d shell dumpsys activity exit-info com.starpilot.starview | grep -E "timestamp=|reason=|description=" | head -24`
- Android's crash records with the stack (works for any version): `adb -d shell dumpsys dropbox --print data_app_crash | grep -E "^Package: com.starpilot|^Timestamp:|^[a-zA-Z.]*(Exception|Error)|^\s+at com\.starpilot" | tail -30`
- Android's freeze records: `adb -d shell dumpsys dropbox --print data_app_anr | grep -A60 '"main"' | head -90`
- What started StarView's process and why: `adb -d shell logcat -d -b main,system | grep -E "StarView/Update|Start proc [0-9]+:com.starpilot.starview|Background activity|Abort background" | tail -15` (the tablet seems to drop the app's Log.i lines; Log.w shows).
- The app's own files (may not exist): crash `files/last_crash.txt`, freeze (from 2.85.4, AnrWatch) `files/last_anr.txt`, read with `adb -d shell run-as com.starpilot.starview cat files/last_anr.txt`.
