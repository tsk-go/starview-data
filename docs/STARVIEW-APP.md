# StarView and StarLock app source (Nov 11, 2026)

Kept in two places, the same text: this file in tsk-go/starview-data (`docs/STARVIEW-APP.md`) and
`claude/starview-app-source.md` in the StarView project on claude.ai. Update both together.

Both apps' source now lives in **tsk-go/starview-data** (public), Gradle project `app/`:
- `app/app` — StarView (tablet). Recovered from the 2.84.1 APK (Kotlin source was lost), checked method by method against its bytecode. Real decompiler bugs found and fixed on the way (endless loops in RoadShape/Hpms/VoiceDsp/curve editor, doubled corner points, takeovers logged twice, inverted camera-config flag).
- `app/starlock` — StarLock (phone). Recovered from 2.19 the same way; its library dex files rebuild byte-identical, only the app's code differs.
- `app/app/compile-stubs` — compile-only exception stubs (Kotlin has no checked exceptions); never packaged.
- `docs/tools/` — the comparison and scanning tools used for the recovery, and the off-device rendering test (see its README). `docs/pending/` — work written but not yet landed.

## Releases and updates
- Workflow `.github/workflows/starview-app.yml` builds both on every push to `main` that touches `app/`.
- A new `versionName` publishes a release: StarView `v<version>` (`StarView-<version>.apk`), StarLock `starlock-v<version>` (`StarLock-<version>.apk`, never marked "Latest").
- In-app updates: StarView Settings › Tablet › About › Check for updates; StarLock Updates › Check for updates (from 2.19.1).
- **Automatic updates (2.85.8, owner's choice Nov 11) — confirmed working end to end Nov 11:** every push to `main` with a new versionName reaches the tablet by itself ~1 min after the release — **also while driving**. Switch "Install updates automatically" (on by default, warning text) in Settings › Tablet › About. So: never push an unreviewed version to main; drafts stay on side branches. **Ask the owner before every release** (the session's safety check refused one push to main until he said go).
  - `AppUpdate.startAuto` (MainActivity.onCreate): daemon thread, GitHub `releases?per_page=10` once a minute with `If-None-Match` (a 304 is tiny and not counted against the limit); 403/429 -> 15 min pause; one try per version per 30 min; only an asset in state "uploaded"; never opens the "allow installs" screen by itself.
  - Install without the confirmation screen: `setRequireUserAction(USER_ACTION_NOT_REQUIRED)` + manifest `UPDATE_PACKAGES_WITHOUT_USER_ACTION` (Android 12+, self-update; tablet is Android 16, targetSdk 35 qualifies). Manual "Check for updates" installs are tap-free too.
  - Reopening after the install (Android closes the app and doesn't reopen it). Tested on the tablet: MY_PACKAGE_REPLACED's `startActivity` and the alarm-clock PendingIntent are both **blocked** by Android's background-activity rules (2.85.9 stayed closed). What works (2.85.10+): with "display over other apps" (SYSTEM_ALERT_WINDOW) allowed, `AppReplacedReceiver` (goAsync) adds a 1x1 TYPE_APPLICATION_OVERLAY window, starts MainActivity 0.5 s later, removes the window after 4 s (Android 15+ lets an SAW app start activities only while one of its windows is visible).
  - Where it comes back (2.85.12, owner's wish; confirmed with 2.85.13): `AppUpdate.inFront()` (own process importance == IMPORTANCE_FOREGROUND; 125 = only the LinkService) decides before the install. On screen -> marker "front", reopens on screen (+ the `Relaunch` alarms as extras). Another app in front or screen off -> marker "back", no toast, no alarm; MainActivity is started with extra `sv_back` + NO_ANIMATION and calls `moveTaskToBack(true)` in onCreate (and onNewIntent), so it runs again (comma link, turn signals, lane prompts, RTK corrections live in MainActivity; LinkService is only a keep-alive) behind the other app — at most a short flicker. The reopen behaviour of an update is the *installed* (old) version's: the first update after a change still behaves the old way.
  - The permission: `adb -d shell appops set com.starpilot.starview SYSTEM_ALERT_WINDOW allow` from the comma (HOME=/data/starview/adbhome) — only sticks once the installed version declares the permission (2.85.10+; on 2.85.9 it stayed "default"). Granted on the owner's tablet Nov 11. Settings › Tablet › About shows "Open again after an update" with an Allow button while it isn't granted (a reinstall / new tablet needs it again).
  - Comma-side backstop (openpilot patch 72, fork history 42): written and tested, NOT yet in tsk-go/openpilot (that session had no `GIT_SIGNING_KEY_B64`). The patch is `docs/pending/openpilot-patch72-reopen.diff` with how to land it. starviewd `Hub._reopen_check` from `tablet_flag_tick` — car on, tablet mode, tablet connected in the last 5 min, then no data client for 8 s -> `adb shell pidof com.starpilot.starview`; no process -> `_tablet_wake`. Every 20 s, 5 tries per drop; a running process is left alone. Test `starview/tests/test_reopen.py`. No longer needed for updates; still useful after a crash while driving. **Before committing, change it to leave StarView alone when another app is in front (`_tablet_front()` not StarView and not the launcher) — promised to the owner, so it never pops up over another app.**
- Drafts the owner hasn't approved go on a side branch (e.g. `navmap-fade`, `wheel-editor-map`, `map-free-size`), not `main`.

## How StarView is built: the hybrid (2.86.0, Nov 11)
Why: the recovered source is a decompiler's copy, and its mistakes (wrong casts, int instead of decimal, loops that never end) only show when that code runs — the Fix-button freeze on the lane card (2.85.13, `LaneFixDialog$Road.getER` looping) was one more. The owner wanted the root fixed, not patched again. So the shipped APK is no longer just our build: `app/hybrid/build.sh` (run by the workflow after Gradle) takes **2.84.1's own compiled code for everything we didn't change on purpose** and our build only for our own changes.
- Inputs: our Gradle APK, the original 2.84.1 APK (orphan branch `hybrid-base`, sha256-checked) and apktool 2.10.0 (its GitHub release, sha256-checked). Resources, manifest, native libs and assets are our build's; only the `classes*.dex` are replaced. Resource IDs stay 2.84.1's (`app/app/stable-ids.txt`, aapt2 `--stable-ids`) because the original code has them as numbers.
- Whole classes (`merge.py`): every class of 2.84.1 ships as it was, except `FEATURES` (our new or rewritten classes: HudLayout, NavOverlay/NavCardView/NavMapView/NavPos, AppUpdate…, Relaunch, Overlay, AnrWatch, R) and classes 2.84.1 doesn't have.
- Method by method (`methodmerge.py`, `decisions.py`, `patches.py`) for the classes we changed: MainActivity (with the screen tick `MainActivity$uiTick$1`), SettingsActivity, MapPane, HudEditor, WheelButton, UiSettings. Every method is 2.84.1's, except: `patch` = 2.84.1's code plus a few smali lines (written by `genpatch.py` from anchors) that call a small new method of ours named `hyb…` (in our source next to the code it stands for; our source calls it at the same place so both builds behave the same) or swap a constant / drop a block; `build` = our method (only `layoutMap`, `wireControls$lambda$136`, `floating_delegate$lambda$172` and UiSettings' defaults list, checked to equal 2.84.1's plus the `nav_map` item); new methods are always ours. Anything those need that 2.84.1 lacks (javac's anonymous classes, d8 accessors) comes along renamed `…$hyb…`; 2.84.1's private members they use lose `private` (or go through Kotlin's `access$` accessor).
- Checks, all in build.sh, any failure stops the release: `guard.py` — a changed source file must be in FEATURES or a method-level class, and every method that differs from the recovered source as first finished (`base.json`, from commit 755431e's build; `changes.py`) must have a decision; a method shipped as 2.84.1's code (`orig` / `patch`) carries the digest of our source at decision time, so editing it later fails the build until the patch is updated (`guard.py DIR --digests` prints the new ones). `check.py` — every call / field between the two halves resolves with the right access, static-ness, invoke kind, no final field written from outside. `verify.py` — register check of every changed method like Android's verifier (numbers vs objects vs long pairs vs unset, every path incl. catch blocks): no complaint on 3,035 of 2.84.1's own methods, and it catches a planted mistake (d8 re-dexing does not). CI builds with JDK 21 like base.json.
- **Changing StarView from now on:** edit the source as usual. If guard says a method "ships as 2.84.1's code", either port the change as a patch (add it in `genpatch.py`, run `genpatch.py ORIG_SMALI app/hybrid/patches.py`, record the digest) or make it `build` after checking that method by hand. New classes and new methods need nothing. Local run: `app/hybrid/build.sh app/app/build/outputs/apk/debug/app-debug.apk <2.84.1 apk> <apktool jar> out.apk`.
- Result in 2.86.0: of StarView's code, only our own new code and those three small methods come from our build; everything else, including the whole driving-screen tick, is the code 2.84.1 shipped.

## Finding freezes / crashes on the tablet
All from the comma, one block (`export HOME=/data/starview/adbhome` first):
- Why StarView last closed (crash / freeze / update / swiped away, newest first): `adb -d shell dumpsys activity exit-info com.starpilot.starview | grep -E "timestamp=|reason=|description=" | head -24`
- Android's crash records with the stack (works for any version): `adb -d shell dumpsys dropbox --print data_app_crash | grep -E "^Package: com.starpilot|^Timestamp:|^[a-zA-Z.]*(Exception|Error)|^\s+at com\.starpilot" | tail -30`
- Android's freeze records: `adb -d shell dumpsys dropbox --print data_app_anr | grep -A60 '"main"' | head -90`
- What started StarView's process and why: `adb -d shell logcat -d -b main,system | grep -E "StarView/Update|Start proc [0-9]+:com.starpilot.starview|Background activity|Abort background" | tail -15` (the tablet seems to drop the app's Log.i lines; Log.w shows).
- The app's own files (may not exist): crash `files/last_crash.txt`, freeze (from 2.85.4, AnrWatch) `files/last_anr.txt`, read with `adb -d shell run-as com.starpilot.starview cat files/last_anr.txt`.

## Version history
- 2.84.2 (Nov 10): first build from the recovered source + Check for updates. **Crashed at start on the tablet**: the GPS card's decompiled code cast each GPS fix to a collection (ClassCastException in GpsSummary.of).
- 2.84.3 (Nov 10): fixes that crash and the same mistake in ~15 other places (route list, object detection, Galaxy home, Scene view lanes/streets, sensors page, theme color picker). Lesson: the decompiled methods' auto-added casts aren't covered by the call/string comparison — `cmpcast2.py` (value source → cast type, per method, vs the original dex) finds them. Install 2.84.3 by hand (2.84.2 can't reach its update button). Confirmed working by the owner.
- 2.85.0 (Nov 10): navigation the StarPort way:
  - Turn card = HUD widget `navCard` ("Navigation - turn card"): arrow, distance, street, "Then" chip, miles | minutes left, ETA, progress bar, lane strip within 0.5 mi (lanes from the tablet's own route copy, `Nav.nextLanes`). Tap = full navigation screen (the old tap-to-collapse / hold-to-cancel are gone). Shows only while the comma is guiding a route.
  - See-through map = new HUD widget `navMap` ("Navigation - see-through map", setting `nav_map`): street lines from the tablet's offline OSM data (`OsmRoads.near`) and the route ahead, heading up, zoom by speed. Code in `NavOverlay.kt` (`NavOverlay`, `NavPos`, `NavCardView`, `NavMapView`). Both draw a sample while the editor is open.
  - Split screen removed: the navigation pane (MapPane) is full screen, its banner is the same card at the top centre; Back and its arrow close it. With it closed, `navTick` still calls `Nav.track` (lanes, progress, spoken directions).
  - Recovery bugs fixed (found from the owner's video: blank map, "No directions for this route", pane not resizable): `Nav.decodePolyline` returned after the first point (all routes empty); map tiles placed with integer division (all off screen); ~20 more integer divisions that were decimal in the original (Scene projection, detector, voice resampler, synth, VASM editor, ...); int math that was long in the original (storage sizes > 2 GB, HPMS varints, ...); `OsmRoads.streetHeading` missing `continue`. Tools: `cmparith.py` / `cmparith2.py` (division / conversion / long-vs-int opcode counts per method vs the original dex), `onceloop.py` (loops whose body always exits), `dupinc.py` (if-block repeating the loop step).
- 2.85.1: an orange / red openpilot alert closes the full-screen map (alerts are drawn inside the road view, which the map covers).
- 2.85.2: the see-through map keeps redrawing (5x a second, one pending redraw) even when it first came up without a position.
- 2.85.3: full-screen map froze ("isn't responding") and was solid blue: the route line was drawn with width `n = 1090519040` (float 8.0's bits read as an int by the decompiler) — now dp(8). A scan for float/double bit patterns used as numbers found no other in use. Picking a destination returns to the driving screen after Go; the full-screen map is never restored at start; the see-through map shows whenever the car is on. Screen editor: Scene/camera, Where to?, Map, Bookmark, Voice, Quick buttons, battery saver pill, favorites bar and the "why it's easing off" chip are widgets (`HudLayout.adoptLate`, ids `hud*` in values/ids.xml).
- 2.85.4: freeze after setting a destination — `LaneAhead.findDrop` looped forever (decompiler turned "same lane count, nothing to do" into `continue`, skipping `k++`); found from the tablet's ANR trace. New scanner `skipinc.py` finds no other. Editor preview 72% / panel 28%, panel buttons in two rows. `AnrWatch.kt` records freezes.
- 2.85.5: see-through map drawn in a layer: faint shade (`SHADE` argb 120,10,14,22), all four edges faded out (two DST_IN linear gradients), street names along the streets via drawTextOnPath (upright, clipped to the clear middle, kept off the route, the car and each other; note Android's `RectF.union(x, y)` only moves the far edge in an else branch — compute boxes by hand). Classic colors: card argb(240,18,19,22) with a faint white edge, white text, navigation blue rgb(66,133,244) for route / progress / car. Icons get their own paint (they used to take the last shape's transparency, so arrows looked dim).
- 2.85.6 (Nov 11): crash when tapping **Presets** in the screen editor (owner hit it Nov 11 09:22 on 2.85.5): `HudPresets.saved` cast the saved-layouts key sequence (`asSequence(keys)`, a one-time `ConstrainedOnceSequence`) to `Iterable`; now iterates the keys directly. Audit after it: every remaining explicit collection cast on a reused decompiler variable (158 sites, script `castsrc.py`: each `(List|Iterable|Collection|Map|Set|ArrayList) varN` with the variable's last assignments) and every explicit number-box cast (`(Double|Integer|Float|Long) varN`, 61 sites) checked by hand — no other wrong type. The ~100 Pair/Triple component casts flagged by cmpcast2 come from generic signatures javac checks, so they're safe.
- 2.85.7 (Nov 11): steering wheel widget always draws `ic_wheel` and rotates by `-steeringAngleDeg` (setting `rotating_wheel`) in experimental mode too (`WheelButton`). Screen editor preview 80% / panel 20% (`HudEditor`). See-through map is tall: 250 x 440 dp (`activity_main.xml`); over the Scene view `light = sceneOn` (set in uiTick) uses `SHADE_LIGHT` argb(60,10,14,22), the camera view keeps argb(120,…). Previewed to the owner first (render test `docs/tools/render/PicTest.kt`: wheel, map, whole editor at 2944x1840 xhdpi — the tablet is 1472 x 920 dp at density 2.0).
- 2.85.8 (Nov 11): free-size widgets — `HudLayout.Item(free = true, defW, defH)` (only `navMap`, 250 x 440 dp): `State.w` / `h` (dp) and `zoom`, saved as "w", "h", "z"; `apply` sets the view's real LayoutParams size (scale stays 1; an old uniform scale becomes w x h once). Screen editor: dragging the corner of a free widget changes width (sideways) and height (up/down) separately; Edit widget shows Width / Height − / + (20 dp steps, shown as % of default) and for the map "Map zoom" − / + (x1.25 steps, 0.33-4x). `NavMapView`: line widths in dp (`u = density`), zoom 177 dp per 180 m ahead x owner's zoom (speed still widens the view up to 700 m ahead), sample streets in metres around the car so the editor shows zoom and size truly. Plus automatic updates (see above).
- 2.85.9 (Nov 11): a new map zoom / size showed only after something else redrew the map — `NavMapView`'s 5x-a-second redraw stopped while the editor was open and never restarted after Done; now it keeps going (2x a second while editing), `stopHudEdit` invalidates the map, and a changed zoom snaps instead of easing. First automatic update: installed ~40 s after the release, did not reopen.
- 2.85.10 (Nov 11): reopen after a self-update via a 1-pixel overlay window (see above); manifest `SYSTEM_ALERT_WINDOW`. 2.85.11: same code, released only to test it — reopened by itself.
- 2.85.12 (Nov 11): an update while another app is in front comes back behind that app (see above). 2.85.13: same code, test release — the owner stayed in another app, StarView updated behind it and was running when he switched back. Confirmed.
- 2.86.0 (Nov 11): the hybrid build (see "How StarView is built"). Triggered by a freeze on 2.85.13 (Nov 11 16:10, while driving: lanes wrong -> Fix on the lane card -> `LaneFixDialog$Road.getER` looped; AnrWatch's `last_anr.txt` had it) and the owner's report that StarView lagged since the rebuild. No feature change.
- Lesson: every route-dependent feature (lanes ahead, lane suggestions, exit signals, Scene route) ran for the first time in the recovered code in 2.85.x, because routes never decoded before — expect more first-run bugs there. Same for rarely used buttons (Presets had never been tapped since the recovery).
- Off-device rendering check: Robolectric 4.14.1 with `@GraphicsMode(NATIVE)` renders the views to PNG — `docs/tools/render/` (setup in `docs/tools/README.md`; the Gradle additions are never committed). The editor renders with reflection on `HudEditor.selected` / `tab` + `refresh()`.
